# バックアップ・復旧 — 営業パイプライン・受注予測管理

## 1. バックアップ方針

データベースは **Neon PostgreSQL**（プロジェクト: `mirai-sales-pipeline` / tiny-cake-63492081）にあり、
Neon の **Point-in-Time Recovery（PITR）** と **ブランチ** をバックアップ・復旧の基盤とする。

| 項目 | 設定/方針 |
|---|---|
| ベースバックアップ | Neon 管理（自動） |
| PITR | Neon の履歴保持（history retention）。現在 24 時間（`history_retention_seconds: 86400`）。重要データのため拡大を推奨（7日以上） |
| 論理バックアップ | 定期の `pg_dump`（スキーマ + データ）を別ストレージへ保存（推奨: 月次） |
| テストブランチ | 統合テスト用に `test` ブランチ（br-damp-union-awiqj0zn）を常設 |

## 2. 復旧手順

### PITR による復元（誤更新・データ破損時）

1. Neon コンソール（または API）で対象ブランチの **Restore** を実行（復元時点を指定）
2. 復元先ブランチでデータ整合性を検証（件数・監査ログ・主要テーブル）
3. 問題なければアプリの `DATABASE_URL` を復元先ブランチへ切替（Cloudflare Worker Secrets 更新 → 再デプロイ）
4. 検証後、旧ブランチは保持（ロールバック用）または削除

### 論理バックアップ（pg_dump）

```bash
# スキーマのみ
pg_dump "DATABASE_URL" --schema-only -f backup_schema_YYYYMMDD.sql

# データのみ（本番は業務時間外・負荷低減のため PITR を基本とする）
pg_dump "DATABASE_URL" --data-only -f backup_data_YYYYMMDD.sql

# 完全バックアップ（小規模向け）
pg_dump "DATABASE_URL" -f backup_full_YYYYMMDD.sql
```

保存先: 社内ストレージ / クラウドストレージ（暗号化）。バックアップファイルは Git へコミットしない。

## 3. RPO / RTO（目標・初期値）

| 指標 | 目標 |
|---|---|
| RPO（許容データ損失） | PITR 保持時間内（現状 24h → 推奨 7日へ拡大）。論理バックアップ併用時は直近バックアップ時点まで |
| RTO（復旧目標） | 4 時間以内（ブランチ復元 + 接続切替 + 検証） |

## 4. 復元テスト（定期実施）

| 頻度 | 作業 | 判定基準 |
|---|---|---|
| 月次 | PITR で一時ブランチへ復元し、主要テーブル件数・スキーマ整合性を確認 | 復元成功・件数一致 |
| 四半期 | 復元ブランチへの接続切替をドライラン（本番に影響しない時間帯） | 切替手順が完遂できること |
| 月次 | `pg_dump` の取得とリストア確認（別ブランチへ） | リストア成功 |

実施結果は運用台帳（operations.md）に記録する。

## 5. 注意事項

- 復元は必ず**別ブランチ**へ行い、検証後に本番へ切替える（直接上書きしない）
- PITR 履歴保持期間の延長は Neon コンソールのプロジェクト設定で変更可能（課金に影響）
- バックアップ・復元テストの失敗は P1 として記録し、翌月までに解消する
